# Touch recorder and replay (M1-04 hunt)

## What was added
- `iBoardKeyboard/TouchRecorder.swift` (`#if DEBUG` only): ring buffer of the last 400 records, flushed every 1 s and in
  `viewDidDisappear` to `Library/Caches/touchlog.json` in the App Group container. Hooks in `KeyboardViewController`:
  `handleTouch` (every phase, id, `UITouch.timestamp`, x, y, key index, key kind, lag = CACurrentMediaTime minus the
  timestamp) and `handle(KeyEvent)` (insert with character COUNT only, altBegan/altEnded/altCancelled, openEmoji,
  hlOn/hlOff). Never a character. Allowlisted in `scripts/audit-privacy.allowlist` (WRITE); audit passes.
- Shared format in `Packages/IBoardUI/Sources/IBoardUI/TouchLog.swift` (`TouchLogRecord`, `TouchLogFile`, `TouchLogRing`).
- `scripts/touchlog.sh [udid]` pulls the file via `devicectl` into `build/touchlog/`.
- Replay: `Tests/IBoardUITests/TouchLogReplayTests.swift` has `replay(_:)` (feeds the machine, ticks at 30 Hz between
  records) and a fixture test (`Fixtures/fast-taps.json`). To analyse a device log: copy it into `Fixtures/`, load it with
  `loadFixture`, compare `replay(log).insertCounts` / `events` with the logged `insert` / `altBegan` records.
  Swipe and spacebar-drag arbitration are not replayed.

## Bug found and fixed (reproduced by a failing test)
`KeyboardInputMachine.touchDown` with a repeated touch id (missed end event) calls `touchUp(id:time:)` with no point.
If that slot had its alternates popup open, the machine emitted `alternatesEnded(.zero)`. `AlternatesSelection.end(at:)`
runs `move(to: .zero)`: y=0 is above the strip's bottom, so it enters the strip and clamps x to cell 0, the FIRST option.
For `i` the first option is `î`, which is exactly the symptom ("Tyîng"). A release over the key itself returns the
origin letter (`originText`), so a normal lift is fine; only the positionless path produced `î`.
Fix: a positionless lift now emits `alternatesCancelled` and types the key's own letter. Test:
`MissedEndAlternatesTests.missedEndWhileAlternatesOpenTypesOwnLetterNotFirstOption` (failed before, passes now). One
existing test (`genuineLongPressStillWinsWhenLiftedAfterTheDelay`) relied on a positionless lift and now passes a point.

This explains why the popup result is always `î`, but NOT yet why the popup opens or why another key drops. The popup
only opens if an `i` press outlives 0.45 s by `systemUptime` before its lift is processed. The device log will show it:
look at `altBegan` records, the `lagMs` of the preceding touches, and whether an `ended` for that id is missing or arrives
with a late `ts`. The dropped key should show up as a `began` with no matching `insert`.

## Code hunt results (no other reproducible cause)
- Auto-shift after `T`: `setShift` only emits `shiftChanged` (grid recolour), it does not call `setLayout`. `setLayout`
  runs only from `relayoutIfNeeded` when the `LayoutKey` changes (size/safe area/traits/kind), and keeps a touch if the
  key identity at the same index is unchanged, so a shift change cannot mark touches committed.
- Jitter: `touchMoved` ignores motion under 10 pt (`slideSwitchDistance`); moves only reach `alternatesMoved` once
  `isAlternates` is already set, so they cannot start the popup.
- Release over strip: `end(at:)` picks the option under the finger only if the finger entered the strip, otherwise `i`.
