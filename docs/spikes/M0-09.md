# M0-09 Spike: misc keyboard behaviors

Environment: iOS 27.0 simulator, iPhone 12 (fresh device `spike-M0-09`, created with `simctl create` because the
source sim was booted and cannot be cloned). Throwaway diagnostic keyboard (a red probe view plus buttons that print
results into an on-screen label; no typed text was logged or persisted). Driven with `axe`.

## Questions
1. P-15: can a keyboard extension's views draw above the extension view's bounds?
2. `UILexicon` contents and refresh cost.
3. Pasteboard behavior and `detectPatterns` with and without Full Access.
4. Haptic latency.

## Method
- Top edge: child `UIView` (red, 120x100) placed at y=-60 so 60pt lies above `view.bounds`; `view.clipsToBounds = false`.
- Lexicon: `requestSupplementaryLexicon` timed with `CFAbsoluteTimeGetCurrent`, then a second call for refresh cost.
- Pasteboard: `hasStrings`, `hasURLs`, `detectPatterns([.probableWebURL,.probableWebSearch,.number])`, and
  `UIPasteboard.general.string`, run with `RequestsOpenAccess=true` and Full Access first OFF (default) then ON
  (enabled via Settings > General > Keyboard > Keyboards > iBoard > Allow Full Access).
- Host: a throwaway SwiftUI text field in the iBoard app (Safari taps were unreliable). The iBoard keyboard was
  selected through the globe long-press menu.

## Results

| # | Probe | Result |
|---|---|---|
| 1 | Draw above bounds | NOT drawn. Only the 40pt of the probe inside the view is visible, cut exactly at the view's top edge (`assets/top-edge-probe.png`). Keyboard `view.frame` = (0,0,390,216), window frame identical, superview is a plain `UIView`. |
| 2 | `hasFullAccess` | false by default, true after the Settings toggle (a confirmation alert is shown by iOS). |
| 3 | Lexicon, Full Access ON | 31 entries, 1 of them a shortcut (userInput != documentText); first call 5 ms, refresh 0 ms. Callback arrives on a background thread (`Thread.isMainThread == false`). Simulator has no real contacts, so 31 is a floor not a representative figure. |
| 4 | Lexicon, Full Access OFF | No result was observed: the completion never printed after two attempts. Treat as "not delivered / empty" but NOT CONFIRMED (taps via axe are flaky). |
| 5 | `hasStrings`/`hasURLs`, Full Access OFF | Readable and accurate (`hasStrings=true`, `hasURLs=false`), no prompt. |
| 6 | `detectPatterns`, Full Access OFF | Works: returned `probable-web-search` for a plain-text clipboard, 59 ms. |
| 7 | `detectPatterns`, Full Access ON | Returned `probable-web-url` for a copied URL, 4 ms. |
| 8 | `UIPasteboard.string`, Full Access OFF | Returns `nil` silently (no prompt), even though `hasStrings == true`. |
| 9 | `UIPasteboard.string`, Full Access ON | Returned the 19-char URL; no paste prompt/banner appeared (clipboard was copied by the same app, so cross-app prompt NOT TESTED). |
| 10 | `detectPatterns` completion thread | Called on a NON-main thread. A closure inheriting @MainActor crashes the extension under Swift 6 (`BUG IN CLIENT OF LIBDISPATCH: Block was expected to execute on queue com.apple.main-thread`); the keyboard then silently falls back to the system keyboard. Hop to main explicitly. |
| 11 | Cross-app pasteboard prompt (`simctl pbcopy` source) | Reads were issued (log shows item request) but the on-screen result was not captured and the keyboard view disappeared afterwards for unknown reasons. NOT TESTED conclusively. |
| 12 | Haptic latency | NOT TESTABLE in the simulator (no Taptic Engine). Needs a device (M0-03). |

## Conclusions
- P-15 holds: nothing can draw above the extension view in the simulator. All transient UI (alternates, previews, chips)
  must live inside the keyboard's own area; the key preview balloons on the top row must be clipped or redesigned.
  Real-device recheck is still advisable but not required to proceed.
- `UILexicon` is only usable with Full Access, and its callback is off-main; it is cheap (5 ms, cached 0 ms with 31 entries).
  Real-device cost with a large contact book is NOT TESTED.
- Without Full Access the pasteboard is effectively opaque for content (`string == nil`) while `hasStrings`/`hasURLs`
  and `detectPatterns` still work. This supports M6-05 (clipboard code fallback): detect a number pattern without Full
  Access, read the value only with Full Access. Whether iOS shows a paste prompt on cross-app reads with Full Access
  is NOT TESTED here and must be checked on device.
- Any pasteboard/lexicon completion must be handled with an explicit hop to the main actor.

## Impact on ROADMAP
- P-15: confirmed, update its "recheck in M0-09" note to "confirmed in simulator (iOS 27.0); recheck on device".
- M6-05 (Depends: M0-09): detectPatterns usable without Full Access; string read needs Full Access; prompt behavior open.
- No locked decision in section 4 is contradicted.

## Facts for ROADMAP section 5
- Extension views cannot draw outside `view.bounds` (iOS 27.0 sim): a child at y=-60 is clipped at the top edge.
- `hasFullAccess` is false until the user enables Full Access in Settings; extension can still run with `RequestsOpenAccess=true`.
- `UIPasteboard.hasStrings/hasURLs` and `detectPatterns` work without Full Access; `UIPasteboard.string` returns nil without it.
- `requestSupplementaryLexicon` and `detectPatterns` completions are not on the main thread; Swift 6 isolation assertion crashes the keyboard if they touch UI directly.
- Simulator lexicon: 31 entries (1 shortcut), 5 ms first call, 0 ms refresh. Real contacts and haptics NOT TESTED.
- Selecting a third-party keyboard in the sim: set `AppleKeyboards` to `en_US@sw=QWERTY;hw=Automatic` THEN `app.iBoard.keyboard`
  (that order, plus reboot) so the globe key appears; long-press the globe (`axe touch --down --up --delay 1.2`) and
  tap the iBoard row with `axe touch --down --up`. Plain `axe tap` is unreliable on keyboard UI.
