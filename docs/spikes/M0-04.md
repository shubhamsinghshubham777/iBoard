# M0-04 Spike: translucency

Environment: iOS 27.0 simulator, iPhone 12 (fresh device `spike-M0-04`, deleted afterwards), Xcode 27 build, driven with
`axe`. Throwaway probe keyboard (buttons a-e switch the background mode; nothing typed was logged). Host: Safari
showing a page served from 127.0.0.1 with bright horizontal stripes (red/yellow/teal/blue/green) and a text field.
Screenshots in `M0-04-assets/` (downscaled to 700 px tall side).

## Question
Can a keyboard extension show the host app through its background on iOS 27, with which API, and what does the system
keyboard itself look like? What can the "Native" and "Native Glass" themes be (F10, R-02)?

## Method
Probe keyboard height 260 pt; the mode view is inserted at index 0, pinned to `view` edges, with controls on top:
(a) `UIInputView(frame:inputViewStyle:.keyboard)`, (b) `UIVisualEffectView(UIBlurEffect(.systemChromeMaterial))`,
(c) `UIVisualEffectView(UIGlassEffect())`, (d) `UIView` with `.clear` background, (e) nothing added (default).
Light and dark appearance (`simctl ui appearance`). Baseline: system English (US) keyboard in the same host.

## Results

| # | Background | Light | Dark | Host visible? |
|---|---|---|---|---|
| S | System keyboard (baseline) | `system-light.png`: frosted glass, stripes clearly visible and blurred; keys are near-white rounded glass tiles that pick up the stripe colours; rounded top corners | NOT captured (only iBoard views captured in dark) | Yes, blurred, strongly tinted |
| a | `UIInputView(.keyboard)` | `light-a-inputview.png`: pale blurred stripes | not captured separately | Yes (identical to e) |
| b | `UIVisualEffectView` systemChromeMaterial | `light-b-visualeffect.png`: near-opaque white sheet, stripes essentially hidden; also covers the system glass below | `dark-b-visualeffect.png`: opaque dark grey-blue sheet | NO, it hides it |
| c | `UIGlassEffect` | `light-c-glass.png`: translucent frosted layer, stripes faintly visible (lighter, hazier than the default); visible rectangular edge/border at the sheet bounds | `dark-c-glass.png`: dark translucent, stripes visible, thin light border | Yes, attenuated |
| d | Clear `UIView` | `light-d-e-clear-default.png`: identical to default | not captured | Yes (same as e) |
| e | Default (no view) | same file as d | `dark-default.png`: dark tinted glass, stripes visible dimmed | Yes, blurred |

Observation that matters: with no background of our own (a, d, e) the keyboard already shows the host blurred. The
glass is drawn by the system container that hosts the extension (including the globe/mic bar and rounded top corners),
not by our view. Our own effect views are drawn on top of it.

## Conclusions
- Host content DOES show through, blurred and tinted, in iOS 27.0 simulator light and dark, for free: leave the
  extension background clear (or `UIInputView(.keyboard)`, which looks identical).
- We do not control that backdrop. Everything we add (b, c) can only cover or tint it. A `UIVisualEffectView` blur (b)
  is a regression for "Native": it hides the host. `UIGlassEffect` (c) keeps translucency but reads as a second
  layer with a visible edge over the system glass; it is not the same material as the system's.
- "Native" theme: clear background (no own backdrop) plus key tiles drawn like the system's (near-white/dark-fill
  rounded rects, SF Pro). That is the same backdrop as the system keyboard. Keep the system's bottom bar (globe,
  mic) in mind: it is outside our 260 pt view and keeps its own look.
- "Native Glass" theme: feasible as per-key `UIGlassEffect` tiles (not tested here) or semi-transparent fills over
  the system backdrop; a full-sheet `UIGlassEffect` was tested (c) and looks layered, not native. Recommend: do not
  add a full-sheet effect; vary only key fills/tint. Per-key glass was NOT TESTED.
- Custom theme backgrounds (images/colours, M8) simply replace the system look; translucent alpha < 1 lets the
  system backdrop through.
- Memory / GPU cost: NOT MEASURED (no Instruments run). Qualitatively: (a), (d), (e) add no effect layer; (b) and (c)
  add an offscreen blur/glass pass over the full 390x260 area, which must be budgeted against M0-03 (extension limit
  76-80 MB on device); simulator cannot give GPU numbers. NOT TESTED on device.
- Not tested: system keyboard in dark mode (baseline), the landscape layout, iPad, reduce-transparency setting,
  real device rendering (the simulator renderer may differ).

## Impact on ROADMAP
- R-02: largely retired. Host see-through works by default; "glass" cannot be faked with our own blur, so design
  Native Glass around the system backdrop (clear background plus glass-like tiles).
- M1-03: use a clear background for the default theme; do not add `UIVisualEffectView`.
- M8-01: Native = clear + system-like tiles; Native Glass = per-key glass/tint over the system backdrop (verify per-key
  `UIGlassEffect` cost on iPhone 12 before committing).
- F10 "possibly true see-through blur" in the §3 scope note can change to: see-through is provided by the system.
- No locked decision in section 4 is contradicted.

## Facts for ROADMAP section 5
- iOS 27.0 sim: the extension host draws a system glass backdrop (blurred, tinted host content, rounded top corners)
  behind any extension view; with no background view the host shows through in light and dark.
- `UIInputView(.keyboard)`, clear `UIView` and no view render identically.
- `UIVisualEffectView(.systemChromeMaterial)` is near-opaque and hides the host; `UIGlassEffect` full-sheet stays
  translucent but looks like a second layer with a visible edge.
- Backdrop cost and per-key glass: NOT TESTED.
